# 模板 02 · 新需求任务单（Feature / Spec Brief）

> 适用：新增功能、新页面、新能力；先写"它是什么、为什么、验收什么"，再谈实现。
> 原则：**意图与证据先于实现**（spec before plan）。大需求先出 spec，评审通过后再拆任务。

---

## A. 需求定义（Spec）

**1. 问题陈述**
- 用户/业务现在遇到什么问题？证据是什么？
- 不解决会怎样？

**2. 目标用户与场景**
- 谁、在什么场景、多久用一次、替代方案是什么。

**3. 目标结果（Outcomes）**
- 用"用户能做成什么"描述，不用"系统实现了什么组件"。

**4. 范围 / 非范围**
- In：最小可用集合（MVP）。
- Out：本版明确不做（写出来，防止范围蔓延）。

**5. 用户故事**
- 作为 <角色>，我希望 <能力>，以便 <价值>。
- 每个故事配 1–3 条验收标准。

**6. 验收标准（Given / When / Then 或 当…应…）**

| 编号 | 场景 | 前置（Given） | 动作（When） | 期望（Then） | 证据 |
|---|---|---|---|---|---|
| AC-1 | 主路径 | | | | E2 |
| AC-2 | 边界 | | | | E2 |
| AC-3 | 负例 | | | | E2 |

**7. 非功能要求**
- 性能/容量、兼容性、安全与隐私、可访问性、国际化、可观测性、成本。

**8. 设计与实现约束**
- 必须复用的组件/接口；禁止改动的地方；技术栈版本；向后兼容要求。

**9. 依赖与风险**
- 依赖项、外部接口、数据迁移、灰度/回滚策略。

**10. 成功度量**
- 上线后看什么指标？多久看？达到什么算成功？

## B. 实现计划（Plan，spec 通过后再填）

- 拆分：任务 1/2/3…（每个任务独立可验收）。
- 顺序与依赖；每步的验证方式。
- 需要人类提供/决定的事项（素材、数据、权限、口径）。
- 预计改动面（文件/模块/语言）。
- 回滚方案。

## C. 交付与验收

- 交付物清单（代码/文档/截图/迁移脚本）。
- 验收人；验收会/走查方式。
- 上线后验证（监控、日志、抽检）。

## D. 常见错误

- 一上来写实现细节，却没写"用户能做成什么"。
- 验收标准是"功能可用"，没有边界与负例。
- 非范围留空 → 智能体"顺手"扩大范围。
- 没有度量 → 上线后无法判断成败。

## E. 最小可用版（小功能）

```text
【问题】____（证据：____）
【目标用户】____
【做】____；【不做】____
【验收】AC-1 ____；AC-2（边界）____
【证据】E2：____
【约束】____；【回滚】____
【授权】改代码可自主；发布等我说。
```
